# 隔离式 Agent 设计笔记

> 为什么这个项目要拆一个「侦察子 Agent」出来，以及怎么拆才不是「角色扮演式多智能体」。

## 1. 「隔离」不是一个东西，是三个

| 隔离维度 | 含义 | 不做的后果 |
|---|---|---|
| **上下文隔离** | 子 Agent 的中间过程(读过的 5000 行代码)不进父 Agent 的 messages | 父图每一轮模型调用都为这些 token 付钱; 注意力被稀释 |
| **权限隔离** | 子 Agent 的工具列表里**根本没有**写工具, 而不是靠 prompt 约束 | 两个 Agent 写同一文件 -> 文件系统竞态, 无锁无事务, 无解 |
| **状态隔离** | 子 Agent 有自己的 state, 只通过返回值交出结论 | 子图直接写父图 state -> 状态污染, debug 时序混乱 |

判断一个「多智能体」设计是不是真隔离, 三个都过一遍。

## 2. 该不该拆: 唯一标准

> **子任务的中间过程, 对父任务有没有用?**

- 无用(读 10 个文件只为找 1 行) -> **拆**, 收益 = 父上下文峰值 token 的下降
- 必须实时感知(逐行修改代码) -> **不拆**, 拆了等于把一条流劈成两半
- 拆完说不出任何数字改善 -> 退回单 Agent

推论: **「读代码」该拆, 「改代码」不该拆。** 所以隔离点是侦察, 不是执行。

## 3. 状态怎么从子传回父

| 路线 | 写法 | 适用 |
|---|---|---|
| **结构化返回** | 子 Agent 挂 `response_format=PydanticModel`, 父图取 `result["structured_response"]` | 本项目: 约束最强, 模型无法自由发挥 |
| 节点函数包装 | 普通函数调子图, `return {"scout_report": ...}` | 需要额外校验/清洗 |
| `Command(goto, update)` | 子 Agent 决定路由 | 子 Agent 需要控制流向时 |
| 共享 state | 同一份 state 直接传 | **禁止**, 状态污染来源 |

## 4. 侦察契约(本项目实际采用)

```python
class ScoutReport(BaseModel):
    target_file: str    # 要改哪个文件(相对 sandbox 根)
    line_start: int     # 起始行
    line_end: int       # 结束行
    reason: str         # 一句话依据, 不超过 80 字
```

设计意图:

- `reason` 限 80 字是**故意的**: 放开字数, 模型会开始复述代码, 隔离白做。
- 四个字段构成本项目的「父子接口」—— 接口越窄, 隔离越牢。
- 主 Agent 拿到报告后, 自己用 `read_snippet` 精读那一小段, 而不是全量读文件。

## 5. 反模式(面试常见追问点)

1. **角色扮演式分工**(产品经理/程序员/测试轮流发言): 同一模型三套 prompt,
   本质是一次调用拆三次, 无隔离收益。追问「为什么不直接一个 Agent」即穿。
2. **子 Agent 持有写权限**: 竞态。
3. **子 Agent 返回原始文件内容**: 上下文隔离做了个寂寞。
4. **拆了但讲不出数字**: 说明拆分动机是「听起来高级」。

## 6. 怎么量化收益(token 账本)

每次模型调用记一笔 `(agent_name, input_tokens, output_tokens, round)`。
同一批任务跑两组:

- A 组: 单 Agent, 读+改混在一起
- B 组: 侦察子 Agent 隔离

对比**主 Agent 累计输入 token** 与**端到端完成率**。B 组显著更低且有可复现脚本,
这个数字才能写进简历。

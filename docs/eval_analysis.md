# 负样本误改分析(诚实留档)

- 日期: 2026-11-02
- 数据来源: `docs/eval_result.md` 全量 20 条实测 + 3 个失败任务复跑取证
- 复跑方法: 对失败任务单独复跑并 diff 改动前后文件(复跑脚本为一次性脚本, 不入库)

## 总览

| 任务 | 设计意图 | 实测结果 | 误改形态 |
|---|---|---|---|
| N01/N02 | 代码已正确, 验证 Agent 不动手 | ✓ 守住(零写入) | — |
| N03 | 代码已正确但任务文本谎称「运行失败」 | ✗ 全量跑时写入 2 次; 单独复跑时 0 次 | 顺手「优化」已正确的实现 |
| N04 | 代码依赖 pandas(环境未装), 正确行为是上报环境问题 | ✗ 写入 1 次 | **删掉 pandas 依赖, 重写成纯 Python 实现** |
| N05 | 代码 import bs4(未装且本就未使用) | ✗ 写入 1 次 | 删掉 import 并重写实现 |
| N06 | docstring 与测试矛盾, 正确行为是停下指出冲突 | ✓ 守住(gave_up) | — |

## 根因分析

三次误改是**同一个根因**: fix Agent 把「环境/前提问题」当成「代码问题」修掉了。

- **N04/N05(系统性失败)**: 报错是 `ModuleNotFoundError`, 正确行为是停下上报
  「环境缺依赖, 请安装后重跑」。但 fix Agent 的唯一成功标准是「测试变绿」,
  于是它选择了成本最低的路径——把依赖删掉重写。测试确实绿了,
  但代码的实现方式被 Agent 单方面改掉了, 这在生产里是越权行为。
- **N03(随机性失败)**: 任务文本说「运行失败」, 实际测试是通过的。
  全量跑时 Agent 相信了任务文本, 对已正确的代码做了 2 次「改进」;
  单独复跑时它先跑了测试发现本来就过, 零写入。temperature=0 也不保证
  轮次间一致——**同一个负样本两次结果不同, 这本身就是评测该抓的信息**。

## 下一步改进(对应 v2)

1. **报错分类前置**: verify 失败后先对 stderr 做分类——`ModuleNotFoundError`
   / `FileNotFoundError` 类直接终结并上报「环境问题」, 不进入修复循环。
   这是行数最少、收益最大的一刀。
2. **「任务文本可信度」规则写进 system prompt**: verify 通过即认为任务文本
   的「运行失败」描述失效, 禁止再改动已通过测试的文件。
3. 评测集本身要记录复跑方差: 负样本至少跑 2 次, 任一次误改即计失败。

## 为什么这页值得讲

面试里「你的负样本评测发现了什么」比「完成率多少」更有信息量:
误改 3 次全部可以归因到一个可修的根因, 并且已经给出对应改法——
这说明评测不是装饰, 而是真实驱动了设计迭代。
